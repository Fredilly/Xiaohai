## Prepared artifacts

- `Dockerfile.production-web`: builds both TypeScript/React sites from one audited source revision; embeds _same-origin_ `/api` access (`VITE_API_BASE_URL=""`), serves compiled files from Caddy only, no Node runtime or secrets in the final web image.
- `Caddyfile.production-web`: automatic HTTPS for the two named sites. Each routes `/api`, `/api/*`, `/health`, `/ready` to the **explicitly supplied separate production API** and serves its own SPA, without an accidental Vite development or staging proxy.
- `production-web.compose.yml`: an isolated web-only Compose project. It has no PostgreSQL/Redis/worker/API containers or staging volumes. It expects `WEB_REVISION` and `PRODUCTION_API_UPSTREAM` to be set; it does **not** itself deploy production.
- `scripts/production-web-preflight.mjs`: read-only local config validation; rejects placeholder, insecure, staging or self-referential API origins and unpinned revisions.
- `Caddyfile.production-api` / `production-api.compose.yml`: separate HTTPS API hostname and API/Worker containers. The production DB and Redis are **external dependencies**, not created or migrated by this bundle; secrets live in ignored `deploy/production.env` and never enter the public web image.
- **For one dedicated production server:** `Caddyfile.production-unified` / `production-unified.compose.yml` serve **all three** domains using **one** Caddy HTTPS entrypoint and private-network API/Worker containers. This avoids binding ports 80/443 twice. `pnpm preflight:production-unified` requires a clean exact Git revision shared across API/Worker image tags and web build. Use this topology **instead of**, never alongside, the split web/API Compose stacks on the same host.

## Human-operated readiness gates

1. The production API hostname is `api.pamboo.asia`; confirm the dedicated API **infrastructure**, DNS/TLS and clean database/Redis isolation. Do not reuse `staging-api.pamboo.asia` or its database, secrets and volumes. Record a separately reviewed source SHA and restore strategy. The API image tags must be present in the authorized registry; a branch commit alone does not produce deployable GHCR images.
2. Point `store.pamboo.asia` and `admin.pamboo.asia` DNS records (and `api.pamboo.asia` for the unified topology) to the approved **isolated** production server(s). Verify ports 80/443 are free, and never bind on a server already exposing staging Caddy. All three hosts need valid TLS; Caddy obtains certificates only after valid DNS and outbound ACME connectivity exist.
3. Only once independently authorized, check out the exact reviewed commit with a clean working tree. Both preflights require `PRODUCTION_HOST_ISOLATED=true` backed by a **verified dedicated production host**, because `staging-api.pamboo.asia` already owns the existing staging VM's 80/443. For **split deployment** set `WEB_REVISION` to that exact 40-character SHA and `PRODUCTION_API_UPSTREAM=https://api.pamboo.asia`, run `pnpm preflight:production-web`, then `docker compose -f deploy/production-web.compose.yml config`. For **unified one-server deployment**, set `WEB_REVISION=API_REVISION` to the reviewed SHA, run `pnpm preflight:production-unified`, then `docker compose -f deploy/production-unified.compose.yml config`. These are **render-only** checks. Do not build/start until deployment approval, verified private DB/Redis, registry image availability, capacity, port and recovery prechecks are complete.

4. Verify response routing at both sites: `/` serves the correct application, `/api/v1/...` reaches the production API, `/health` and `/ready` show the production API status, deep links survive refresh, HTTPS and browser requests contain no staging/localhost requests. Confirm Staff RBAC and store scope with authorized test accounts; no real stock/payment mutation during smoke checks.
5. Separately configure the company-authorized WeChat AppID and the confirmed production API domain in the WeChat request/upload/download allowlist. A valid website certificate does not substitute for a WeChat real-device domain check. Keep food writes/checkout and payment switches disabled until their own approval and operational acceptance.
