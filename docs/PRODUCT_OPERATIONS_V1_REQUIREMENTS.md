## 1. 目标与适用范围

小海童话 2.0 应能够使用**真实的门店商品数据、实拍商品图片及真实库存**，支持图书、普通商品、食品和饮品。门店工作台与总部后台使用同一套商品、SKU、库存及订单系统；微信小程序读取符合公开展示条件的商品信息。

**可以并行推进真实商品资料准备、商品图片管理、食品库存功能和三端联调**，不要求所有开发任务严格串行。但是，真实数据录入、公开上架、交易支付和生产发布的操作权限及验收条件必须分别满足，不能因为资料已录入就自动对外销售。

本补充文档修正现有系统中“总部才能修改商品主资料，门店只能修改货架、备注及陈列信息”的旧限制。与旧实现或旧需求表述冲突时，本文件反映最新的业务方向；具体代码、迁移和安全权限仍需评审后落地。

## 2. 核心业务原则：门店和总部经营功能一致

**门店工作台和总部后台应拥有相同的日常经营管理功能。** 总部后台相比门店工作台，**额外拥有工作台账号及其角色、权限和授权范围的管理能力**，而不是独占商品、价格、库存或图片编辑权。

| 业务能力 | 门店工作台 Store Web | 总部后台 HQ Admin Web | 消费者微信小程序 |
| --- | --- | --- | --- |
| 新增、查看、编辑商品 | 支持 | 支持 | 查看已公开的商品 |
| 商品上下架、停售 | 支持 | 支持 | 仅展示符合公开条件的商品 |
| 修改商品名称、分类、描述、价格、规格、SKU、条码 | 支持 | 支持 | 只读展示 |
| 上传、更换、管理商品主图与详情图 | 支持 | 支持 | 展示主图与详情图 |
| 图书、普通商品、食品、饮品经营管理 | 支持 | 支持 | 浏览并按可售状态下单 |
| 门店库存、收货、出入库、盘点、调拨、报损 | 支持 | 支持 | 查看可用库存或缺货状态 |
| 订单及相关履约操作 | 支持 | 支持 | 查看、管理自己的订单 |
| **工作台员工账号、角色、权限、数据授权管理** | **不作为门店端的额外管理模块** | **总部独有** | 不适用 |

### 2.1 功能一致不等于数据权限无限制

- 门店和总部应复用相同的商品业务规则、验证逻辑和数据接口能力，而不是维护两份独立商品库。
- 门店用户可以在**被授予的数据范围**内新增、编辑、上下架商品及管理库存；不能凭前端传来的门店 ID 越权修改其他门店的数据。
- 总部可以管理工作台账号、分配角色和授权范围；所有业务权限须由服务端按 **RBAC + Data Scope** 校验。
- 无论从门店还是总部编辑同一条共享商品，都应使用统一的商品 ID、版本号、变更记录及冲突处理机制，避免后写入直接覆盖先写入。
- 对于跨门店共享商品、门店专属商品、跨门店价格是否一致、商品由哪家门店创建后谁能修改等规则，**尚需业务确认**，不得自行假定“所有门店均可编辑所有共享商品”。

## 3. 真实商品资料与三端数据互通

### 3.1 商品统一来源

商品应以统一的 PostgreSQL 商品主数据为准，业务实体包括 `products`、`skus`、`product_media` 等；各门店通过与商品 SKU 关联的库存记录管理本店数量。

建议数据流：

```text
门店工作台 ──────┐
                 ├── HTTPS API ── 商品 / SKU / 图片 / 库存数据库
总部后台 ────────┘                      │
                                       ▼
                            微信小程序读取已上架商品
```

门店和总部任一方在权限范围内新增或修改商品后，另一端以及小程序应从**同一套服务端数据**获取更新，而不是再分别手动录入。

### 3.2 商品基本信息

应支持的商品资料至少包括：

- 商品名称、类别、描述、状态；
- SKU 编码、零售条码、规格、计量单位、价格和可售状态；
- 商品主图及多张详情图；
- 所属或适用的门店，以及按门店核算的库存；
- 图书专属字段：书名、作者、出版社、ISBN 等；
- 食品专属字段：食品类别、品牌、规格、批次/生产日期、有效期或保质期等（见第 5 节）。

图书和非图书商品应共享基础商品和 SKU 结构，但**不能要求食品填写虚假的 ISBN、作者或出版社**。

### 3.3 真实数据使用规则

- 可以先整理商家的真实商品名称、价格、SKU/条码、库存清单和实拍图片，用于建立正式商品档案。
- 新建或批量导入商品应默认以**草稿 DRAFT** 保存，经数据校验、去重、核对之后，再由具备权限的操作人员显式上架。
- 真实库存录入须保留来源、记录操作人员及变更流水；不可直接覆盖未核对的既有库存。
- 正式生产库/共享 Staging 库的批量写入、迁移、真实上架和公开交易，必须先有对应环境授权及备份/回退条件。
- 美萍最终迁移仍遵循原有范围：**图书主数据和当前门店库存**。食品等新增商品资料应走独立录入/导入流程，不得偷偷扩展美萍迁移范围。

## 4. 商品图片与小程序展示

### 4.1 门店和总部都可以管理图片

门店工作台与总部后台均应支持：

1. 选择或上传商品实拍图片；
2. 设置主图及多张详情图，支持排序、替换与移除；
3. 在编辑时预览图片，并清晰提示上传失败、无效格式等错误；
4. 保存后由服务端关联图片与商品，另一后台与小程序读取统一的图片资料。

使用仓库既有的对象存储技术路线（BOS）。上传、访问地址、图片格式、文件大小、归属及权限须有服务端校验。不能为了显示图片而把整个存储桶改成公开读写；小程序需要可访问、受允许域名规则约束的 HTTPS 图片地址。已有 `coverUrl` 可作为兼容字段，逐步扩展为主图与有序图片列表。

### 4.2 小程序展示

- 商品列表展示主图、名称、售价和适合商品类型的摘要；商品详情可展示图片相册、规格/SKU、价格及库存或缺货状态。
- 图书展示 ISBN、作者、出版社；食品与饮品展示各自适用的规格与说明，**不显示无意义的图书字段占位**。
- 商品修改并保存后，小程序能获取最新的公开商品信息。
- 图片加载失败应使用清晰的空状态或占位，不能错误显示其他商品图片或 Logo 充当商品图。

## 5. 食品、饮品与库存管理

### 5.1 商品类型

系统需要支持图书之外的食品和饮品。实现时至少区分两类不同库存逻辑：

- **预包装食品 / 成品饮料**：按件、瓶、盒、袋等 SKU 记录数量，并支持食品批次及有效期管理。
- **现制饮品 / 现制食品**：例如门店现场制作的饮品，若需要自动扣减原材料，应单独设计原料 SKU、配方、耗用、损耗与成品销售关系，不能直接当作预包装商品批次管理。

现制饮品**是否在首批版本实现自动原料扣减、是否仅管理成品销量**仍待业务确认，不应未经确认就引入复杂配方成本系统。

### 5.2 食品库存必须具备的约束

- 按 **门店 + SKU** 管理库存，实际可售数量应扣除已预留、不可售、过期、冻结等数量。
- 预包装食品需要可追踪的批次、生产日期/到期日期或保质期信息及相应数量；根据商品类型处理不适用批次的例外。
- 过期、被锁定、报损或停售的食品不得被当作正常可售库存。
- 入库、销售扣减、退货、盘点、调拨和报损均应保留库存事务记录；并发操作不得让库存变成负数或重复扣减。
- 食品批次的先进先出 / 临期先出策略、食品标签及经营资质核验方式须在上线前按实际经营品类确定。

### 5.3 商品展示不等于有库存可售

当前商品属于公开展示状态并不意味着任何一家门店都有货。商品**上架状态**与**指定门店的实际可售库存**是不同概念：

- `DRAFT` / `INACTIVE`：不应出现在对顾客开放的正常在售列表；
- 已上架但指定门店无库存：应显示缺货或不可购买；
- 已上架且库存可售：允许进入购物流程，但后端在加购、下单/预留、结算等关键环节仍需重新验证库存、状态和并发条件。

不能只靠小程序按钮的禁用状态实现库存安全。

## 6. 关键验收场景

| 编号 | 验收场景 | 预期 |
| --- | --- | --- |
| A01 | 门店工作台创建并编辑商品（含价格、SKU） | 权限内操作成功，记录准确且可追踪 |
| A02 | 总部后台创建并编辑同类商品 | 与门店使用一致的业务规则和结果 |
| A03 | 门店或总部上传、更换真实商品主图及详情图 | 三端能读取相同商品及正确图片，顺序一致 |
| A04 | 未上架草稿商品 | 小程序正常商品列表不可见 |
| A05 | 上架有库存的食品/普通商品 | 小程序能显示正确名称、图片、规格、价格及可售状态 |
| A06 | 无库存、过期、冻结或停售 | 前端显示准确状态，服务端拒绝违规购买或扣减 |
| A07 | 门店 A 的员工访问或修改未授权门店 B | 服务端拒绝，无越权或数据泄露 |
| A08 | 门店和总部同时编辑同一商品 | 版本冲突可识别，不发生静默覆盖 |
| A09 | 门店管理员尝试修改工作台账号权限 | 无该模块/权限，服务端拒绝提权 |
| A10 | 食品收货、盘点、调拨、报损以及过期处理 | 变更流水完整，门店库存和实际可售数一致 |
| A11 | 图片异常、格式错误或外部地址不可访问 | 明确报错/回退，不显示错误商品图片 |
| A12 | 微信真机测试已上架商品、图片和下单 | 与相应环境的真实 API、域名、库存状态一致 |

验收材料必须区分：**代码实现、自动化测试通过、测试环境实际验证、正式生产验收**；CI 全绿不能直接替代真实门店和微信真机的验收。

## 7. 当前代码差距（截至 2026-11-07 的已核对仓库状态）

以下是对当前实现的记录，**不是业务上的功能限制要求**：

- 当前门店商品路由对名称、价格等共享字段仍有写入限制，门店页面以货架、备注、陈列编辑为主；**需改为与总部同等的经营功能**，但保留数据范围校验。
- 总部商品页已有创建/编辑、SKU、售价及封面 URL 基础功能；统一图片上传及多图相册仍需补充。
- 当前微信小程序商品列表、详情读取共享商品 API，但商品展示状态与具体门店实际库存仍需进一步联动。
- 已存在 `products`、`skus`、`product_media`、`store_inventory` 等基础结构，但食品批次、保质期、现制原料配方等尚未构成完整业务闭环。
- 消费者小程序正式版 API 仍使用安全占位配置；门店/总部网页和真实交易也尚未完成最终上线验收。

因此，本文件被加入仓库后**不能视为功能已经上线**。后续应按照协作规范，以独立分支、PR、数据库迁移审核、测试和真实环境验收逐步交付。

## 8. 仍需确认的业务细节

> 下列事项不影响先开展 UI、API 设计、真实商品资料整理和离线测试；但在实现跨门店共享写入、真实批量数据修改或食品库存迁移前必须定稿。

1. 商品归属：门店创建的商品是否默认成为所有门店都可选用的共享商品，或只属于创建门店？
2. 定价规则：同一 SKU 是否全国/全门店统一价格，或允许每个门店独立售价？
3. 跨店编辑：门店对其他门店已经在售的共享商品修改价格、名称时，采用直接同步、影响预览还是逐店生效？
4. 食品经营种类：首批主要是预包装零食、瓶装饮料，还是还包括现制咖啡/茶饮、现场制作食品？
5. 现制库存：首批是否需要通过配方自动扣除咖啡豆、茶叶、奶类、糖浆、杯子等原料库存？
6. 食品的实际经营资质、商品标签及临期处理要求，以商家经营品类和适用规则为准。

## 9. 交付与安全边界

**可同步开展：** 真实商品数据表格与图片整理、共享商品页面和 API 改造、食品库存数据模型与离线测试、商品图片处理、三端联调准备。

**需要额外授权：** 对现有共享 Staging / 生产数据库写入真实商品或执行迁移、批量上下架、对外真实支付、对象存储权限变更、正式版本发布。

沿用现有项目安全约束：`RBAC + Data Scope`、服务端权限、PostgreSQL 库存事务、版本冲突检查、审计、环境隔离和人工发布审批。**本补充需求不授权自动迁移数据库，不授权清理 Docker 数据，不代表 Staging 或生产环境已准备好。**


## 2026-11-24 已确认决定（取代上文相应待定项）

用户在 #208 连续开发会话中已明确确认：

1. **共享商品资料，但每个门店独立售价。** 共用 product/SKU ID；门店关联建立时以 SKU 参考价初始化本店价，之后独立版本化保存。后续修改总部 SKU 参考价不覆盖既有门店价。共享名称等跨店变更仍遵守权限范围、影响确认和版本冲突规则。
2. **首批只完成预包装食品和瓶装饮料。** 现制咖啡/茶饮暂不自动扣料，不在本轮引入配方或原料扣减。

这些决定授权工程实现，不授权在共享数据库执行迁移、录入真实库存、公开上架、真实支付、BOS 权限修改或部署。Fred 继续独立负责安全审计和视觉设计，工程自动化结果不能替代真人审查或真实门店验收。
