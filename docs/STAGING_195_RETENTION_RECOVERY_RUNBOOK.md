## A. Physical storage accounting — no mutation

`scripts/staging-containerd-footprint.py` (Python 3 standard library) measures:

1. Each Docker image's full `RootFS.Layers` (diffIDs) and the containerd chainIDs generated by them.
2. All containerd overlay **committed snapshot metadata** via `ctr -n moby snapshots --snapshotter overlayfs ls` and `usage -b`. Committed usage is supplied by containerd's metadata, not a recursive filesystem `du`.
3. Per-snapshot ownership by **all** local Docker image IDs and descendant snapshot references, distinguishing layers exclusive to only the two candidate release pairs from shared/protected layers.
4. Per-content-blob allocated blocks from read-only `stat`, plus OCI index/manifest/config/layer descriptors read in a bounded 1 MiB-per-document graph. Unknown leases, foreign manifest schemas, missing containerd metadata or incomplete candidate chainIDs must be reported as **incomplete**, never approximated as zero.
5. Per-pair and combined modeled **maximum** reclaimable bytes (exclusive unpacked snapshots + exclusive local OCI content), with a separate explicit `guaranteed_reclaim_bytes=0` pending an actual owner-authorized deletion and measured `df` difference.

The script does **not** delete anything or invoke snapshot `prepare`, `diff`, `unpack`, GC, `docker image rm`, or `prune`. It requires root read access to `/var/lib/containerd` and may return `MEASUREMENT_INCOMPLETE` if Docker/ctr namespace, metadata or permissions do not match expectations. Do not circumvent that failure with recursive root scans or claim exact reclaimed bytes before deletion.

Reproducibility: execute only the exact reviewed script from the immutable PR commit after checking its content/sha; run it once during a low-load window on staging through Workbench. It contains no writes but metadata calls still impose small I/O; stop on unexpected output. Never paste credentials or raw deployment configuration.

## C. Future bounded retention (not activated)

The `--steady-state-execute` mode is also disabled by default and **requires the genuine successful-deployment revision** and all normal exact-ID preconditions/owner plan. Unlike capacity-emergency `--execute`, it may remove obsolete approved SHA-tagged pairs after a successful deployment even when disk is already below 70%; this avoids uninterrupted image accumulation. At most two fully approved pairs per invocation. It is deliberately **NOT** wired to `.github/workflows/staging-deploy.yml`: activation needs a separate code/review/rollout owner decision and a clearly defined process for generating a fresh exact-ID manifest after each successful deployment.

A deterministic **90-day offline model** includes shared base layers, initial 26 release pairs, six fixed historical/HOLD releases, current and two moving rollback releases, plus stopped-container references. With two obsolete-pair retirements after each successful deployment, the modeled unique-layer footprint reaches a plateau after the initial backlog is drained. This is simulation, **not the measured steady-state bytes** on the existing staging host, which depend on actual image layers and leases. The hardcoded five HOLD identities in the safety script remain protected until a separately approved policy change.
