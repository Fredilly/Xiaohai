# #208：食品订单、退款与实物流转

状态：集成分支实现，等待独立审核及专属环境 UAT；不是部署授权。

## 已确认规则

共享商品资料，每店独立售价。仅预包装食品、瓶装饮料；现制配方不自动扣料。退款是资金操作，实物回收是独立库存操作，不能互相冒充。

## 决定与事务边界

- 正式选店下单在消费者购物车锁内，按 SKU 顺序取得食品溯源锁和库存行锁；锁定门店价格、商品状态，重算服务端报价。订单、订单项、履约门店、FEFO 分配、预留事件、总预留和清空购物车在同一事务提交。失败完整回滚，原请求键重放原订单。
- FEFO 只分配有效期内、AVAILABLE、分类已核验且祖先链可用的批次；相同到期日以批次 ID 稳定排序。库存总量、总预留与批次及存量分配不符即停止。
- 自提核销、配送发出消费原预留批次，不重新选批次；再次检查到期、冻结/召回和来源链。在原履约事务内，单向转为 SOLD，扣减总量/总预留和各批次量/预留，写一个总 SALE 和相应批次 SALE、预留 SALE 事件。
- 未付取消只释放原预留；未履约的已确认全额退款释放原预留并结束履约。召回批次可以释放占用，但状态不恢复 AVAILABLE。已履约退款不增加 on_hand，不生成退货批次。
- 实物接收显式指定原 SOLD 分配、实际数量、内部凭证和请求键；原订单门店范围校验，累计退回不超过原分配。新建 HELD 批次，保留原类型、生产日和到期日；ADJUSTMENT_IN 总流水、PHYSICAL_RETURN 批次流水与不可变退货证据同事务。原订单及退款状态不变。相同原分配+凭证编号唯一，网络重试不能另记同一实物。
- 调拨复用既有 DRAFT → SUBMITTED → IN_TRANSIT → RECEIVED 单据。操作人员须有两店范围及 inventory.transfer；发出按可用批次分摊、写 TRANSFER_OUT 与不可变来源；接收按来源逐批建立 HELD 目的批次、写 TRANSFER_IN，保留来源批次关联及日期。普通库存路径不能绕过食品批次写入。
- 每个 SKU 使用跨店事务溯源锁，所有食品状态变更、分配、履约、退货、调拨在库存锁之前取得；多 SKU 按 ID 升序。源批次召回与下游扣减序列化。递归来源校验拒绝循环、未知分类、超过 32 层、到期、冻结/召回祖先。单次工作集超过 500 批次失败即停止；不截断后当作可售。
- 资金退款支持原 PAID、PICKUP_READY、DELIVERING、COMPLETED 或已取消订单；失败关闭时恢复原状态。真实 Provider 行为仍需既有支付验收，测试仅为合成 Provider。

## 数据库强制约束

0046 原历史保持不变。0047 扩展批次 SALE 和预留变化约束：订单项的分配总和/统一状态、事件序列、订单 SKU/履约门店、SOLD 与物理 SALE 流水对应均在数据库检查。0048 增加实物退货、调拨来源表、不可变/单向状态及数量检查、双边调拨流水完整性、递归来源函数和退款原状态集合。0049 限制同分配同接收凭证只能登记一次。

预留不是物理数量变化，因此使用专用预留事件，不伪造零数量库存流水。食品实体流转均同时记录总流水和批次流水，既有延迟总和约束继续执行。

## 开关与未声称完成的事项

`FOOD_STOCK_WRITES_ENABLED=false` 和 `FOOD_CHECKOUT_ENABLED=false` 默认保持。结算开关要求库存开关同时为 true，任何非明确字符串均不能开启。不得因代码/CI通过自动修改环境。关闭后仍允许对已有订单取消或确认退款时安全释放原预留，不能把顾客库存永久占用。

代码与合成 PostgreSQL 回归不证明真实门店数据、照片、微信设备、浏览器交互、生产支付、资质或部署已经通过。500 批次工作集与 32 层来源上限须在目标数据预检；超过时停止并设计分页/归档，不删历史或跳过对账。
